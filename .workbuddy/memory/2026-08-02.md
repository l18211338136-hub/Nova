## 审计日志筛选器修复（用户反馈）
用户反馈审计日志页筛选器存在 3 个问题：文案不对应、条件查不出结果、日期显示原始格式。根因分析与修复：

1. **布尔筛选文案硬编码**：`DataTableColumnFilter` 组件对 `filterType: 'boolean'` 硬编码了 "Active"/"Inactive" 选项，审计日志的"成功/失败"语义不符。
   - **修复**：组件改为读取 `columnDef.meta.booleanOptions.{trueLabel, falseLabel}`，无配置时 fallback 到原来的 Active/Inactive（不影响 users 表的"启用/停用"）。审计列配置 `{ trueLabel: t('Success'), falseLabel: t('Failed') }`。

2. **日期筛选值静默丢失（核心 bug）**：`occurredOn` 列 `filterType: 'date'` 的 UI 输出 `[min, max]` 数组，但 `useTableUrlState` 配置的是 `type: 'string'`——数组在序列化时 `typeof [] !== 'string'` → 赋空串 → 变 undefined，**日期筛选永远发不到后端**。
   - **修复**：`useTableUrlState` 中 `occurredOn` 改为 `type: 'array'` + 自定义 serialize（数组 join 逗号）/ deserialize（逗号 split 数组），与 `buildODataFilter` 的数组 range 逻辑对接（生成 `OccurredOn ge ... and OccurredOn le ...`）。

3. **文本筛选占位符通用化**：所有文本过滤器 placeholder 都是硬编码的 `t('Filter...')`（显示为"过滤..."）。
   - **修复**：`DataTableColumnFilter` text 分支改为读 `meta.filterPlaceholder`，无配置时 fallback 原值。审计列分别设为事件类型/账号/IP 地址。

- 以上修改均为**向后兼容**：`column-filter.tsx` 的改动通过 meta 可选属性扩展，不影响 users 等既有表格。`tsc -b` + `vite build` 均通过。

## 顶部进度条频繁闪烁修复（两阶段）
用户反馈：每次查询（筛选/分页/排序）顶部都会闪一下进度条，体验差。

**阶段一（初版修复，仍残留闪烁）**：
- 根因：`src/components/navigation-progress.tsx` 用 `react-top-loading-bar` 监听 `useRouterState().status`。TanStack Router 把 **search 参数变化（改 URL 的筛选/分页/排序）也视为 pending 导航**，于是每次查询都触发 `continuousStart()` → 顶部进度条闪一下。
- 初版修复：用 `lastSettledPath` ref 记录上次 idle 的 pathname；仅在 pending 期间 `location.pathname` 与上次不同（真正的页面切换）才 `continuousStart()`，仅 search 变化（pathname 不变）不显示；settle 后 `complete()`。

**阶段二（用户反馈"还是会闪"——根因在 `complete()`）**：
- 真正残留闪烁的原因：search 变化虽不 `continuousStart()`，但路由仍经历 `pending→idle`，idle 分支无条件调用 `ref.current?.complete()`。而 `react-top-loading-bar` 的 `complete()` 在**未 start 过**时仍会闪出一条满进度条再淡出，于是每次查询都闪。
- 最终修复：新增 `isActive` ref，只有确实 `continuousStart()` 过才置 `true`；idle 分支仅在 `isActive` 为 `true` 时才 `complete()` 并复位。这样纯 search 变化（pathname 不变、未 start）走到 idle 时**完全不碰进度条**，彻底消除闪烁；真正的页面跳转（pathname 变、已 start）照常 start→complete。`tsc -b` 通过（`navigation-progress.tsx` 零报错）。
- 经验：**`react-top-loading-bar` 的 `complete()` 不能无条件调用**，必须与 `continuousStart()` 成对并加"是否启动过"的守卫，否则在不该显示的场景也会闪。

## 审计日志事件筛选 + 登录原因修复
用户反馈两个问题：①事件类型筛选条件查不出结果；②登录事件的"原因"列显示 `-`，希望显示登录方式（密码登录/邮箱登录）。

### 问题 1：事件筛选查不出结果
- **根因**：DB 存储英文枚举名（`LoginSuccess`/`LoginFailed` 等），但前端 eventType 筛选器是自由文本框（`filterType:'text'`），用户输入中文"登录"→OData 生成 `contains(EventType,'登录')`→永远匹配不上英文枚举值。
- **修复**：
  1. `column-filter.tsx` 新增 `filterType === 'select'` 分支：渲染 `<Select>` 下拉框，选项从 `meta.selectOptions`（`{value,label}[]`）读取，选中发送原始 value 给后端。
  2. `tanstack-table.d.ts` 扩展 `ColumnMeta`：`filterType` 增加 `'select'`；新增 `selectOptions`、`booleanOptions`、`filterPlaceholder` 可选属性（消除之前被 suppress 的类型报错）。
  3. `audit-columns.tsx` eventType 列改为 `filterType:'select'`，配置 5 个枚举选项（value=英文名，label=i18n 翻译）。OData 层无需改动——`contains(EventType,'LoginSuccess')` 对精确匹配同样有效。
- **向后兼容**：新增 select 类型不影响既有 text/boolean/date/number 筛选器。

### 问题 2：登录原因列为空
- **根因**：`LoginCommandHandler` 发布 `LoginSuccess` 事件时未传 `reason` 参数（第 182 行 `new AuthAuditEvent(...)` 缺少 reason 实参）。

## 邮箱登录不写审计日志（根因修复）
用户反馈：用邮箱登录时审计日志表没有插入记录。
- **根因**：邮箱验证码登录走的是独立命令 `EmailLoginCommandHandler`（与密码登录的 `LoginCommandHandler` 不同）。该 Handler **从未注入 `IDomainEventDispatcher`，也从未 `PublishAsync(new AuthAuditEvent(...))`**，所以邮箱登录无论成功失败都不写审计日志；而密码登录的 `LoginCommandHandler` 有完整审计发布逻辑。
- **修复**（`EmailLoginCommandHandler.cs`）：
  1. 新增 `using Nova.Framework.Domain.SeedWork;`（IDomainEventDispatcher）与 `using Nova.Modules.Identity.Application.Events;`（AuthAuditEvent）。
  2. 构造函数注入 `IDomainEventDispatcher _dispatcher`（DI 已注册，与 LoginCommandHandler 同）。
  3. 登录成功生成 Token 后发布 `LoginSuccess`（tenantId/user.Id/true/"邮箱登录"）。
  4. 邮箱存在但 `FindByEmailAsync` 返回 null（数据不一致）时发布 `LoginFailed`（reason "邮箱对应的用户不存在"）——此分支已有有效 tenantId，可落库。
  5. 验证码错误 / 无租户映射 / 多租户待选 等分支发生在定位租户之前，无 tenantId 无法落库，保持不记录（与消费端"找不到租户即丢弃"行为一致）。
- 注：前端走 `LoginCommand`+邮箱账号 与 走 `EmailLoginCommand` 两条路径现已都能正确写审计日志。

## 邮箱登录登出失败 + 审计日志不显示（刷新令牌存储不一致）
用户反馈：①邮箱登录后审计日志仍无记录；②登出时部分记录显示"刷新令牌不存在或已吊销"（失败）。
- **根因（两个问题的统一根源）**：`EmailLoginCommandHandler` 存储刷新令牌的方式与 `LoginCommandHandler` **完全不同**：
  - `LoginCommandHandler` → `RefreshTokenStore.AddAsync()` → 存储 key 为 `("NovaApp", "RefreshTokens")`，值为 JSON 数组 `[{"Token":...,"Revoked":false,...}]`
  - `EmailLoginCommandHandler`（旧代码）→ `userManager.SetAuthenticationTokenAsync(user, "NovaApp", "RefreshToken", ...)` → 存储 key 为 `("NovaApp", "RefreshToken")`（单数！），值为管道分隔字符串 `"token|expiry"`
  - **后果 A**：登出时 `LogoutCommandHandler` 调用 `RefreshTokenStore.GetAllAsync()` 读 `("NovaApp", "RefreshTokens")`，永远读不到邮箱登录存的 token → 报"刷新令牌不存在或已吊销"（截图里密码登录的 session 登出成功、邮箱登录的 session 登出失败，完全吻合此规律）。
  - **后果 B**：上一轮给 `EmailLoginCommandHandler` 加的审计日志代码虽然正确，但**后端未重启所以没生效**；且即使生效了，token 存储不一致也会导致后续登出等操作异常。
- **修复**：将 `EmailLoginCommandHandler` 的 Refresh Token 存储从 `SetAuthenticationTokenAsync(user, "NovaApp", "RefreshToken", pipeString)` 改为 `RefreshTokenStore.AddAsync(userManager, user, new RefreshTokenEntry{...})`，与 `LoginCommandHandler` 完全一致。编译通过（0 错误）。
- **用户需重启后端**才能使本次所有改动（审计日志发布 + token 存储修复）生效。
